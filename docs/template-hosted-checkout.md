# Templates: Courses-compatible hosted payment flow

Templates reuse the existing Razorpay.me merchant checkout used by Courses. This does **not** provide automatic payment verification: browser callbacks and buyer references only create a pending review. A super admin must check the captured, unrefunded merchant payment, exact buyer/reference and GST-inclusive amount at `/app/template-orders` before approving. Approval allocates one immutable GST invoice and emails the invoice and private copy links. Duplicate payment references cannot pay two cart orders.

No new gateway credentials are needed for this manual flow. `TEMPLATE_CHECKOUT_ENABLED=false` disables new checkouts. The API-verified gateway implementation remains available only when its existing flag and all Razorpay keys/webhook configuration are present. Hosted orders remain manual even if gateway settings subsequently change.

Shared Courses checkout now preserves paise, so ₹998 plus 18% GST is paid as ₹1,177.64, not rounded to ₹1,178. Existing whole-rupee course amounts are unchanged. Templates without configured copy links remain unavailable. Hosted cloud subscriptions and Workspace prices are unchanged.

Seller tax identity comes from the primary Sheetomatic organization's saved invoice profile, with its existing Sheetomatic seller defaults. Existing 18% GST handling is used with intra-state CGST/SGST and interstate IGST. SAC 997331 is configured for standard software-use copies; the business should confirm its classification with its GST adviser. No existing invoice or catalogue price row is rewritten.

## Deployment

Preserve the original production source and its pinned preparation chain. The reviewed release reconstructs the previous storefront using `scripts/shop.mjs --prepare-only`, verifies checksums before replacing its scoped files and updates only the TemplateCheckout Prisma model. Never deploy the whole historical checkout over production.

`scripts/template-migrate.mjs` checks the Vercel project, production Neon target and primary seller workspace. It applies only these two additive migrations transactionally, with checksum tracking and an advisory lock:

- `20261020060000_template_checkout` — cart orders and invoice counter
- `20261020120000_template_hosted_checkout` — receipt review and admin audit fields

It never runs other pending migrations. Run read-only preflight before the build, then apply after tests and the production build pass. Existing products, customer records and legacy orders are untouched. Rollback to the previous deployment leaves these unused additive tables in place; do not drop them once orders exist.

## Verification

Integration tests use isolated local PostgreSQL with gateway/email mocks, never production. Browser checks at 390px and 1440px verify cart operations, GST, pending receipt recovery and downloads locked until mocked admin confirmation. No real charge or customer email is generated by the checks.

The thumbnail covers are responsive, colour-coded product illustrations with distinct workflow labels, not claimed screenshots or customer metrics. Cloud subscription cards remain separate.
